# Audit SnapEnv — 29 juin 2026

## Verdict

SnapEnv est une bonne base de démonstration : le modèle de données est lisible,
FastAPI/Celery/PostgreSQL/Redis/ArgoCD forment un ensemble cohérent et les 18 tests API
passent. En revanche, le produit n'est pas encore capable de garantir qu'une MR dispose
d'un environnement correspondant à son dernier commit.

**Décision recommandée : NO-GO production, GO pour poursuivre un prototype contrôlé.**

Les blocages principaux sont l'absence de build d'image dans la CI, le déploiement lancé
avant la fin de la CI, l'absence de vérification de santé ArgoCD, et l'absence de contrat
fiable pour fournir les secrets et les valeurs au chart de preview.

## Ce qui fonctionne déjà

- API FastAPI structurée par routes et schémas Pydantic.
- Modèle PostgreSQL adapté au suivi PR → pipelines → stages → environnement → événements.
- Validation HMAC GitHub quand `GITHUB_WEBHOOK_SECRET` est renseigné.
- Découplage API/worker avec Celery et Redis.
- Diffusion multi-processus prévue via Redis Pub/Sub.
- Images applicatives exécutées avec un utilisateur non-root.
- Ressources Kubernetes demandées et limitées pour les quatre workloads du chart.
- CI avec lint, typage, SAST, détection de secrets et tests.
- Infrastructure Terraform/Ansible reproductible pour un laboratoire mono-nœud.

## Risques et écarts

### P0 — bloquants fonctionnels

1. **La CI ne construit ni ne pousse d'image.** Le fichier `.github/workflows/ci.yml`
   s'arrête après les tests, alors que le README et le worker attendent une image
   `pr-<numéro>-<sha7>` dans GHCR.
2. **Le déploiement part trop tôt.** L'événement GitHub `pull_request/opened` arrive avant
   la fin de GitHub Actions. Même après ajout du job de build, ArgoCD pourra tenter de
   tirer une image qui n'existe pas encore.
3. **Le succès est optimiste.** Le worker marque l'environnement `RUNNING` dès que
   l'API ArgoCD accepte la création de l'Application. Il n'attend ni `Synced`, ni
   `Healthy`, ni une réponse HTTP de la preview.
4. **Une mise à jour ne déploie pas le nouveau tag.** L'Application suit la branche,
   mais son paramètre `image.tag` reste celui du premier commit. Le pipeline est pourtant
   marqué `SUCCESS` immédiatement.
5. **Le chart de preview n'a pas de contrat de configuration viable.** Le même chart
   déploie API, worker, PostgreSQL et Redis pour chaque PR. L'Application ArgoCD ne fournit
   pas les identifiants PostgreSQL requis ; une preview standard ne peut donc pas devenir
   saine.
6. **La suppression du namespace n'est pas garantie.** Supprimer une Application ArgoCD
   en cascade supprime ses ressources suivies, mais il faut vérifier explicitement la
   disparition du namespace et du PVC. Il n'existe ni TTL, ni balayage de réconciliation
   pour les environnements orphelins.
7. **L'idempotence Celery est incomplète.** Après le premier `commit`, une relivraison de
   `handle_pr_opened` voit la PR existante et quitte, même si le worker s'est arrêté avant
   la création de l'environnement. Les exceptions ne déclenchent pas de politique de
   retry applicative et certains échecs sont capturés puis considérés comme réussis par
   Celery.

### P1 — sécurité et exploitation

- Si le secret webhook est vide, toute requête est acceptée. Ce comportement doit être
  réservé à un mode local explicite et le worker doit refuser de démarrer en production.
- Dashboard, REST, métriques et WebSocket sont publics ; CORS autorise toutes les origines
  avec les credentials.
- Les endpoints documentés sont servis en HTTP. Grafana utilise `admin/admin` et ArgoCD
  expose son interface en mode insecure dans le playbook.
- Les tokens GitHub/ArgoCD sont rendus comme variables d'un Deployment et restent lisibles
  dans les objets Helm/Kubernetes. Préférer un `existingSecret` alimenté par External
  Secrets, SOPS ou Sealed Secrets.
- Le worker utilise le projet ArgoCD `default`, tandis que l'AppProject restrictif
  `snapenv` existe mais n'est pas appliqué par le provisioning.
- Aucun ServiceAccount/RBAC dédié, NetworkPolicy, Pod Security Context complet, quota de
  namespace ou limite du nombre d'environnements n'est défini.
- Les images `postgres:16-alpine`, `redis:7-alpine`, l'image applicative `latest` et la
  plupart des GitHub Actions ne sont pas épinglées par digest/SHA.
- Terraform garde son état local et Ansible exécute deux scripts distants `curl | sh`
  non épinglés.

### P1 — fiabilité et données

- Redis n'a pas de persistance. Un redémarrage peut perdre les tâches en attente.
- PostgreSQL est mono-réplique, avec un PVC de 1 GiB et sans sauvegarde/restauration testée.
- Les migrations Alembic sont une étape manuelle après le déploiement.
- `/health` ne vérifie ni PostgreSQL ni Redis ; la readiness peut donc accepter du trafic
  alors que les dépendances sont indisponibles.
- Les événements sont publiés dans Redis avant le commit SQL. Un rollback peut produire
  un événement « fantôme ». Un outbox transactionnel corrigerait ce point.
- Pas de verrou par PR : deux événements proches peuvent modifier simultanément pipeline,
  Application et environnement.
- Le mono-nœud est acceptable pour un lab, mais une panne de VM arrête plateforme,
  previews, base, queue et monitoring.

### P2 — qualité, tests et observabilité

- Couverture totale : **56 %**. `src/workers/tasks.py` est à **16 %** et les services de
  cycle de vie sont entre **19 % et 29 %** : le risque est concentré dans le code le plus
  critique.
- Pas de test contractuel GitHub, ArgoCD, Helm, Terraform ou Ansible ; pas de test de
  reprise après crash, doublon webhook, course update/close ou nettoyage orphelin.
- Le seuil CI de 40 % est trop bas pour un contrôleur d'infrastructure.
- MyPy est strict. Son premier passage a révélé neuf erreurs autour des bibliothèques non
  typées et du patch de métriques ; elles ont été corrigées et le passage final est vert.
- Les métriques couvrent surtout HTTP. Il manque les durées de provisioning, files Celery,
  retries, échecs par cause, âge des environnements, capacité restante et coût estimé.
- Aucun SLO, aucune alerte et aucune politique de rétention des événements, métriques,
  logs, images ou PVC.
- Le README présente plusieurs capacités futures comme acquises. L'écart le plus notable
  est « build + push GHCR », absent de la CI.

## Consommation actuelle

Le chart utilisé pour **chaque preview** déploie actuellement une copie complète de la
plateforme :

| Composant | CPU demandé | CPU limite | Mémoire demandée | Mémoire limite |
|---|---:|---:|---:|---:|
| API | 100 m | 500 m | 128 MiB | 512 MiB |
| Worker | 100 m | 500 m | 128 MiB | 512 MiB |
| PostgreSQL | 100 m | 500 m | 256 MiB | 512 MiB |
| Redis | 50 m | 200 m | 64 MiB | 128 MiB |
| **Total par PR** | **350 m** | **1 700 m** | **576 MiB** | **1 664 MiB** |

Chaque PR demande aussi un PVC de **1 GiB**, quatre pods, quatre images à maintenir en
cache et les objets Ingress/Service/Secret/ServiceMonitor associés.

La plateforme centrale consomme au minimum le même total. À cela s'ajoutent k3s,
ingress-nginx, ArgoCD et kube-prometheus-stack. Le dépôt ne fixe pas les ressources de ces
charts externes : leur consommation doit être mesurée sur le cluster et non supposée.

### Capacité de planification

Le Terraform configure réellement **3 OCPU, 16 GiB RAM et un boot volume de 50 GiB**,
alors que le README annonce 4 OCPU, 24 GiB et 200 GiB. Avec une réserve de sécurité CPU de
20 %, et 1 à 1,5 OCPU pour le système, le monitoring, ArgoCD et la plateforme centrale :

| Nœud | Cap conseillé au départ | Limite temporaire | Motif principal |
|---|---:|---:|---|
| 3 OCPU / 16 GiB | **3 previews** | 5 | CPU et bursts, puis disque |
| 4 OCPU / 24 GiB | **5 previews** | 7 | CPU avant mémoire |

Ce sont des bornes de lancement, pas des mesures de production. À la limite CPU, trois
previews peuvent réclamer 5,1 CPU à elles seules ; le throttling peut donc être important
même si le scheduler accepte leurs requests.

Un profil de preview « application seule » à 100 mCPU / 128 MiB, sans PostgreSQL/Redis/
worker dédiés, multiplierait approximativement la capacité par trois. C'est l'optimisation
architecturale la plus rentable.

### Stockage et réseau

- 10 previews ouvertes = 10 GiB de PVC, hors images, base centrale, métriques et OS.
- Le boot volume Terraform ne fait que 50 GiB ; les 200 GiB OCI mentionnés sont un quota
  de block volumes, pas du stockage automatiquement monté sur le nœud.
- Sans politique de suppression GHCR, 100 images de 250 MiB représentent environ 25 GiB
  avant déduplication des layers.
- Le trafic réseau des previews est probablement secondaire à cette échelle. OCI annonce
  actuellement 10 TiB/mois de trafic sortant Always Free.

### CI et coût GitHub

Les jobs parallèles sont facturés séparément. Une estimation réaliste après ajout du build
est de **13 à 27 minutes Linux par mise à jour de PR** : lint, sécurité, tests, build, scan
et push. Ainsi :

| Mises à jour de PR / mois | Minutes estimées |
|---:|---:|
| 25 | 325–675 |
| 50 | 650–1 350 |
| 100 | 1 300–2 700 |
| 250 | 3 250–6 750 |

Les runners standards sont gratuits pour un dépôt public. Pour un dépôt privé GitHub Free,
la documentation actuelle inclut 2 000 minutes et 500 MiB de stockage partagé ; le Linux
2-core au-delà du quota est annoncé à 0,006 USD/min et le stockage partagé à
0,25 USD/Go-mois. La formule à suivre est :

`coût CI = max(0, minutes - quota) × tarif + stockage moyen au-delà du quota`

Source : [GitHub Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions).

### Coût OCI : attention à la documentation contradictoire

Le coût VM peut être nul **uniquement si la tenancy et la forme sont effectivement
éligibles Always Free**. Les pages officielles consultées ne sont pas cohérentes : la page
générale mentionne jusqu'à 4 OCPU / 24 GiB, une page détaillée mentionne 2 OCPU / 12 GiB,
et la page Ampere annonce 3 000 OCPU-heures / 18 000 Go-heures. Il faut donc vérifier le
badge « Always Free eligible », les service limits et le Cost Analysis de la tenancy avant
de considérer 3 OCPU / 16 GiB comme gratuit.

- [OCI Free Tier](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier.htm)
- [OCI Always Free resources](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm)
- [OCI Arm-based Compute](https://docs.oracle.com/en-us/iaas/Content/Compute/References/arm.htm)

## Architecture cible recommandée

1. Le webhook PR valide signature, dépôt et identifiant de livraison, puis enregistre
   l'intention sans déployer.
2. GitHub Actions teste, construit et pousse une image immuable épinglée par digest.
3. Un événement de fin de workflow réussi déclenche le déploiement de ce digest exact.
4. Un contrôleur idempotent crée ou met à jour l'Application depuis un contrat de preview
   propre au dépôt ; les secrets viennent d'un Secret externe, jamais des paramètres Git.
5. SnapEnv attend `Synced + Healthy`, puis sonde l'URL avant de publier `ENV_READY`.
6. La fermeture de PR déclenche la suppression, et un réconciliateur périodique applique
   aussi TTL, quota global et nettoyage des orphelins.

## Plan d'exécution priorisé

### Lot 0 — rendre le chemin nominal vrai

- Ajouter build/push GHCR et déclencher le déploiement uniquement après succès CI.
- Déployer le digest du commit, pas une branche et un tag supposé.
- Séparer le chart de la plateforme du contrat/chart de preview.
- Attendre la santé ArgoCD et l'URL avant `RUNNING`.
- Rendre secret webhook, repository attendu et credentials Argo obligatoires hors mode local.
- Mettre à jour réellement l'Application lors d'un nouveau commit.
- Critère de sortie : une PR ouverte, mise à jour puis fermée passe un test E2E automatisé
  et ne laisse ni namespace, ni PVC, ni Application.

### Lot 1 — rendre le contrôleur récupérable et sûr

- Machine à états idempotente, verrou par PR, retries bornés et dead-letter queue.
- Outbox transactionnel pour les événements.
- Réconciliateur périodique, TTL par défaut, cap global et ResourceQuota par namespace.
- Secrets externes, RBAC minimal, NetworkPolicies, TLS, auth dashboard et projet ArgoCD dédié.
- Readiness dépendances, migration Job, sauvegarde/restauration PostgreSQL et persistance Redis.
- Critère de sortie : crash du worker à chaque étape sans fuite ni faux succès.

### Lot 2 — industrialiser

- Tests worker/services > 80 %, contrats API simulés, Helm lint/template, Terraform validate,
  ansible-lint et test de charge.
- Métriques métier, SLO de provisioning/nettoyage, alertes capacité et dashboard de coût.
- Rétention automatique des images, artefacts, événements, métriques et volumes.
- Décider explicitement entre lab mono-nœud et production HA.

## Corrections réalisées pendant l'audit

- Génération de `values-local.yaml` restructurée selon les clés réellement consommées par
  Helm ; les valeurs sont échappées via JSON/YAML et le fichier est mis en mode 0600.
- URL ArgoCD interne alignée sur son installation HTTP privée ; suppression de
  `verify=False` dans le client HTTP.
- Unification du WebSocket dashboard avec le bus Redis et suppression de l'ancienne
  implémentation concurrente.
- Documentation de cet audit et modèle initial de capacité/coût.
